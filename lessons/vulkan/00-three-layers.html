Between a call in your program and a pixel on the screen sit three layers: your process, where the bindings and your data live; the driver side, which is the loader, any layers it inserts, and the installable client driver (ICD) that knows the hardware; and the kernel driver with the GPU behind it. Every lesson's panel on the right uses those three lanes, so this lesson walks five enumeration calls, asks which lane answers each one, and then takes apart the picture most people start with: "a command buffer is bytecode plus data that reaches the GPU, whose firmware interprets it".

After this you can:

  • name the three layers and say which one answers each of the five enumeration calls;
  • tell apart shader bytecode, a command buffer and the driver's command stream, and say which of them the GPU's firmware reads;
  • say what a Vulkan layer is and where it sits in the chain of calls.

1. Your call lands in the loader

vkEnumerateInstanceLayerProperties is the first Vulkan call given.jai makes, and the answer never leaves the driver lane's first box. The function lives in libvulkan.so.1, the Khronos loader, which your binary links against. To answer, the loader walks the layer manifest directories it knows (/usr/share/vulkan/explicit_layer.d, implicit_layer.d, the /etc and $XDG equivalents) and parses one small JSON file per layer. No driver has been opened yet; no layer library has been loaded either. A layer is a shared library the loader can insert between your call and the driver, and at this point it is only a file name in a manifest. The two-call pattern, count then fill, is how every Vulkan enumeration works.

layer_count: u32;
result = vkEnumerateInstanceLayerProperties(*layer_count, null);
if result != .SUCCESS {
    log_error("vkEnumerateInstanceLayerProperties (count) failed: %", result);
    return inv, false;
}
layer_props := NewArray(layer_count, VkLayerProperties);
defer free(layer_props.data);
result = vkEnumerateInstanceLayerProperties(*layer_count, layer_props.data);

2. Extensions: what the loader, the layers and the drivers offer

An extension is a named bundle of commands and structures beyond the core API, and the thing to notice is that three different parties can offer one. The loader implements a few itself (VK_KHR_surface, VK_KHR_xlib_surface, VK_EXT_debug_utils). Each driver reports its own. And a layer can add some: VK_EXT_validation_features exists only because the validation layer provides it. Asked with a null layer name, vkEnumerateInstanceExtensionProperties hands back one merged list, loader plus drivers plus whatever implicit layers are enabled, and does not say who contributed what. Asked with a layer's name, it reads that layer's manifest and returns exactly that layer's list, which is why given.jai asks once per layer and why exercise 0 makes you reconstruct the sources.

The null-name query is also the first call that needs a driver's answer, so this is where the loader goes through /usr/share/vulkan/icd.d, dlopens the library each ICD manifest names (libvulkan_radeon.so on this desktop, from radeon_icd.json), and negotiates the loader-to-driver interface version with it. A program that skips the enumerations pays that cost at vkCreateInstance instead; the work is the same.

for layer_props {
    name := copy_string(to_string(it.layerName.data));
    extensions, ok := instance_extension_names(it.layerName.data);   // the layer's own list, from its manifest; the API's buffer is null-terminated, a Jai string is not
    if !ok  return inv, false;
    layers[it_index] = .{name, it.specVersion, it.implementationVersion, copy_string(to_string(it.description.data)), extensions};

3. vkCreateInstance builds the chain

An instance is the loader's object. Creating one is where the loader assembles the dispatch chain that every later call will run through: your call enters a small trampoline in the loader, which jumps to the first enabled layer's implementation of the function; that layer calls the next; the last layer calls back into the loader's terminator, which fans the call out to every ICD it loaded. The first word of the VkInstance handle you get back points at that dispatch table, which is what makes the handle "dispatchable". given.jai asks for no layers and no extensions here, because this instance exists only to reach the drivers in the next step; the test harness's instance, which lesson 1 shows, asks for the validation layer and so gets a chain with one layer in it.

app: VkApplicationInfo;
app.pApplicationName = "exercise-0";
app.apiVersion       = VK_API_VERSION_1_3;
ici: VkInstanceCreateInfo;
ici.pApplicationInfo = *app;
instance: VkInstance;
result = vkCreateInstance(*ici, null, *instance);

Elsewhere

D3D12

Metal

4. Physical devices: the driver asks the kernel

vkEnumeratePhysicalDevices is the first call whose answer comes from below the driver lane. The terminator asks every ICD; each ICD opens the kernel's render node for the hardware it drives and asks the kernel driver to describe the device, and vkGetPhysicalDeviceProperties then reports what the ICD learned: the name, the API version it implements, the vendor's own driver version packing, and the device type. On RADV the render node is /dev/dri/renderD128 and the question is a series of DRM_AMDGPU_INFO ioctls to amdgpu; NVIDIA's driver asks its own kernel module in its own way, which is why driverVersion needs vendor-specific unpacking in exercise 0. Device extensions are the ICD's answer about what the hardware and driver pair can do, so they are asked per device.

devices := NewArray(device_count, Device_Info);
for physicals {
    props: VkPhysicalDeviceProperties;
    vkGetPhysicalDeviceProperties(it, *props);
    extension_count: u32;
    result = vkEnumerateDeviceExtensionProperties(it, null, *extension_count, null);

5. Three things that are not one thing

Now the model to take apart. "The command buffer is bytecode plus data that somehow reaches the GPU, whose firmware interprets it" packs three different things into one word, and they live in three different places.

Shader bytecode is SPIR-V: a stream of 32-bit words your build produced with glslc and your program holds in its own memory. No GPU runs SPIR-V. When you create a pipeline (lesson 3), the ICD compiles those words into the instruction set of the shader cores in front of it, and that native code is what the cores execute. SPIR-V is compiled, not interpreted, and the compiler is the ICD on your CPU.

A command buffer is memory the driver owns. Every vkCmd* call you make while recording appends the driver's own representation of that command to it (lesson 4). It is not a portable format and no part of it is "sent" anywhere at submit time: on RADV the driver writes the hardware's packet format directly into GPU-visible memory as you record, so by the time you submit, the buffer already is the command stream.

The command stream is what the GPU's command processor reads: a microcontroller block (on AMD hardware the PFP, ME and MEC engines, running firmware the kernel uploads) that fetches packets from memory, decodes them, and programs the rest of the chip, including pointing the shader cores at the compiled code. So the "firmware interprets it" half of the picture is right for packets and wrong for shaders. Your program never touches the stream; the ICD writes it and the kernel tells the hardware where it is.

From here on the lanes mean exactly this: CPU is your program and the bindings; driver is the loader, the layers and the ICD, all running in your process; GPU is the kernel driver and the hardware. A box in the driver lane still runs on your CPU; it is in that lane because the code is not yours and its memory is not yours.

Endnotes

VK_LOADER_DEBUG=all

A common alternative to guessing what the loader did is VK_LOADER_DEBUG=all in the environment, which enables the loader's own trace; useful for seeing which manifests it read, which driver libraries it opened and which layers it inserted; the cost is a great deal of stderr and no code change at all.

VK_DRIVER_FILES

A common alternative on a machine with two GPUs is VK_DRIVER_FILES, which pins the loader to one ICD manifest; useful on the hybrid laptop when the integrated GPU keeps answering first; the cost is a per-run environment variable, and the other GPU vanishes from vkEnumeratePhysicalDevices.

VK_INSTANCE_LAYERS

A common alternative to naming a layer in VkInstanceCreateInfo is VK_INSTANCE_LAYERS, which makes the loader enable it for every instance the program creates; useful for trying RenderDoc's capture layer on a program you did not write; the cost is the environment variable and a layer the program did not ask for sitting in its chain.
