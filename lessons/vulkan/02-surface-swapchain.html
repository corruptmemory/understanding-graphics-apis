Nothing in lessons 0 and 1 touched a screen. This lesson is about where pixels go: a surface is the loader's handle to an X11 window, a swapchain is a small set of images the presentation engine owns and lends you one at a time, and a frame is one trip around that loan. Mesa's window-system integration (WSI) code does the talking to the X server, and the exercise owns the four decisions a swapchain rests on.

After this you can:

  • say who owns a swapchain image at each moment, and what acquire and present hand over;
  • explain FIFO, MAILBOX and IMMEDIATE in terms of the vertical blank and the compositor;
  • create a swapchain whose format, extent and image count come from the surface's capabilities rather than from assumptions.

1. A surface is the loader's handle to a window

vkCreateXlibSurfaceKHR never reaches a driver. The loader implements VK_KHR_surface and its platform cousins itself: it allocates a small VkIcdSurfaceXlib record, an Xlib display pointer and a window id behind a common header, and hands you its address as the VkSurfaceKHR. That is the whole object. Every later surface query the ICD answers starts by reading the display and window out of it, which is how one surface type can be shared by every driver on the machine. The second call in create_surface asks whether the harness's queue family can present to it; on this desktop the one family that can draw can also present, but the check is the contract, not the assumption.

create_surface :: (ctx: *Gfx_Context, window: Window) -> (surface: VkSurfaceKHR, ok: bool) {
    sci: VkXlibSurfaceCreateInfoKHR;
    sci.dpy    = x_global_display;
    sci.window = xx window;
    surface: VkSurfaceKHR;
    result := vkCreateXlibSurfaceKHR(ctx.instance, *sci, null, *surface);

2. Ask the surface what it can do

Three queries, all answered by the ICD's WSI code after a round trip to the X server: vkGetPhysicalDeviceSurfaceCapabilitiesKHR, …SurfaceFormatsKHR and …SurfacePresentModesKHR. Mesa's X11 path answers the capabilities with xcb_get_geometry: currentExtent, minImageExtent and maxImageExtent all become the window's current size. Four choices rest on these answers, and each has a trap. The format: prefer B8G8R8A8_SRGB, which lets the hardware do the sRGB encode, but take the first entry when it is not offered. The present mode: FIFO is the only one the specification requires, so it is the fallback. The extent: X11 reports the window size, but Wayland reports 0xFFFFFFFF to say "you decide", and then the window size clamped to the min and max is the answer. The image count: one more than the minimum, so there is always an image to draw into while another is on screen, clamped to maxImageCount, which is zero when there is no maximum.

choose_extent :: (caps: VkSurfaceCapabilitiesKHR, window_w: u32, window_h: u32) -> VkExtent2D {
    if caps.currentExtent.width != 0xFFFF_FFFF  return caps.currentExtent;
    return .{clamp(window_w, caps.minImageExtent.width,  caps.maxImageExtent.width),
             clamp(window_h, caps.minImageExtent.height, caps.maxImageExtent.height)};
}

// minImageCount + 1, clamped to maxImageCount when maxImageCount != 0 (zero means no maximum).
choose_image_count :: (caps: VkSurfaceCapabilitiesKHR) -> u32 {
    count := caps.minImageCount + 1;
    if caps.maxImageCount != 0 && count > caps.maxImageCount  count = caps.maxImageCount;
    return count;
}

3. The swapchain: images the presentation engine owns

The generic rule first: the presentable images of a swapchain are owned by the presentation engine. You never allocate them, you never free them, and you may touch one only between acquiring it and presenting it. vkCreateSwapchainKHR is the ICD's call, and on Mesa the WSI code allocates each image as ordinary GPU memory, exports it as a DMA-BUF file descriptor through the kernel, and hands that descriptor to the X server with a DRI3 PixmapFromBuffers request, so the X server now has a pixmap backed by the very same memory. That is what "shared with the presentation engine" means on this machine: two processes, one buffer, no copy. vkGetSwapchainImagesKHR gives you the VkImage handles, and the views are yours to create, which given.jai does right after.

sci: VkSwapchainCreateInfoKHR;
sci.surface          = surface;
sci.minImageCount    = count;
sci.imageFormat      = format.format;
sci.imageColorSpace  = format.colorSpace;
sci.imageExtent      = extent;
sci.imageArrayLayers = 1;
sci.imageUsage       = .COLOR_ATTACHMENT_BIT;
sci.imageSharingMode = .EXCLUSIVE;
sci.preTransform     = caps.currentTransform;
sci.compositeAlpha   = .OPAQUE_BIT_KHR;
sci.presentMode      = mode;
sci.clipped          = VK_TRUE;
result = vkCreateSwapchainKHR(ctx.device, *sci, null, *sc.handle);

4. Acquire, clear, present: the ownership round trip

A frame is one loan. vkAcquireNextImageKHR asks the engine for an image you may use; on X11 the WSI code waits until the server has reported one of the pixmaps idle, and the semaphore you pass is signaled when the GPU may write into it. Your submit waits on that semaphore at the color-attachment stage, draws, and signals a second semaphore; vkQueuePresentKHR waits on that one and issues a Present PresentPixmap request to the X server, which puts the pixmap on screen at the next vertical blank in FIFO mode, or sooner in the other modes. Under a compositor it is the compositor that reaches the screen: the X server tells it a new pixmap is ready, and it composes your window into its own frame. That is why IMMEDIATE may tear only without one, and why a compositor can add a frame of latency you did not ask for.

Two semaphores, two lifetimes. The acquire semaphore is reused every frame, because the frame fence proves the submit that waited on it has finished. The render-done semaphore is not covered by that fence: the present that waits on it runs in the engine, after the fence. So present_loop keeps one per swapchain image and signals the one belonging to the image it acquired; the validation layer reports a reused one as "may still be in use by VkSwapchainKHR". Lesson 5 opens these objects up properly.

result := vkAcquireNextImageKHR(ctx.device, sc.handle, NEVER, acquired, null, *index);
pi: VkPresentInfoKHR;
pi.waitSemaphoreCount = 1;
pi.pWaitSemaphores    = *done[index];
pi.swapchainCount     = 1;
pi.pSwapchains        = *sc.handle;
pi.pImageIndices      = *index;
result = vkQueuePresentKHR(ctx.queue, *pi);

5. Headless: the same clear without a window

The tests never open a window. The harness target from the template stands in for a swapchain image: an image you own, in the same COLOR_ATTACHMENT_OPTIMAL layout the loop puts a swapchain image into, and a readback instead of a present. record_clear is the piece the exercise owns, and it is the same procedure the windowed program calls each frame: a dynamic-rendering instance over the whole extent whose load operation is CLEAR with your color and whose store operation is STORE, with no draw between begin and end. The two layout transitions around it, one in and one out, are barriers; given.jai and the harness supply them, and lesson 5 opens them up.

record_clear :: (cb: VkCommandBuffer, view: VkImageView, extent: VkExtent2D, color: [4] float) {
    att: VkRenderingAttachmentInfo;
    att.imageView   = view;
    att.imageLayout = .COLOR_ATTACHMENT_OPTIMAL;
    att.loadOp      = .CLEAR;
    att.storeOp     = .STORE;
    att.clearValue.color._float32 = color;

    ri: VkRenderingInfo;
    ri.renderArea           = .{.{0, 0}, extent};
    ri.layerCount           = 1;
    ri.colorAttachmentCount = 1;
    ri.pColorAttachments    = *att;
    vkCmdBeginRendering(cb, *ri);
    vkCmdEndRendering(cb);

Endnotes

VK_EXT_swapchain_maintenance1

A common alternative to one render-done semaphore per image is VK_EXT_swapchain_maintenance1, which enables a fence per present through VkSwapchainPresentFenceInfoEXT; useful for knowing exactly when a present has consumed its semaphore, so per-present objects can be recycled; the cost is enabling the extension and its feature and attaching the fence info to every present.

VK_KHR_xcb_surface

A common alternative to the Xlib surface is VK_KHR_xcb_surface, which takes an xcb_connection_t and an xcb_window_t, the protocol Mesa's WSI speaks underneath anyway; useful when the window code is XCB; the cost is a second surface path and the XCB connection plumbing in the program.

imageUsage with TRANSFER_DST_BIT

A common alternative to rendering into the swapchain image is asking for TRANSFER_DST_BIT in imageUsage and blitting a rendered image into it; useful when the render format or size differs from what the surface offers; the cost is a blit and two more layout transitions per frame.
