Lesson 0 promised that the command buffer and the command stream are one thing seen twice: memory the driver owns, filled with the hardware's own packets while you record. This lesson follows one buffer from the pool to the fence and lands the correction that matters most: vkQueueSubmit2 is an ioctl that names your buffers, not a translation of them. Then it uses the exercise's four overlapping triangles to show the one ordering Vulkan does promise, submission order, and the one it does not.

After this you can:

  • say what memory a vkCmd* call writes, who owns it, and in what format;
  • say exactly what vkQueueSubmit2 does and does not do;
  • predict which draw wins at an overlapping pixel from the submission order across two command buffers.

1. The pool, the buffer, and what begin does

A command pool is the driver's allocator for one queue family, which is why the harness names ctx.queue_family when it creates one and asks for the reset flag so single buffers can be reused. vkAllocateCommandBuffers hands out a buffer in the specification's initial state; vkBeginCommandBuffer moves it to recording, and ONE_TIME_SUBMIT_BIT tells the driver it will be submitted once and freed, so nothing needs to survive the submit. Generically, what sits behind the handle is memory the GPU can read and the CPU can write, reset by begin. On RADV it is a radeon_cmdbuf, an indirect buffer the winsys allocates in GTT, system memory mapped into the GPU's address space, or in VRAM when the CPU can map it; radv_BeginCommandBuffer resets it and emits the preamble that every buffer on this hardware starts with.

cpci: VkCommandPoolCreateInfo;
cpci.flags            = .RESET_COMMAND_BUFFER_BIT;
cpci.queueFamilyIndex = ctx.queue_family;
result = vkCreateCommandPool(ctx.device, *cpci, null, *ctx.command_pool);
begin_buffer :: (ctx: *Gfx_Context) -> VkCommandBuffer {
    ai: VkCommandBufferAllocateInfo;
    ai.commandPool        = ctx.command_pool;
    ai.level              = .PRIMARY;
    ai.commandBufferCount = 1;
    cb: VkCommandBuffer;
    result := vkAllocateCommandBuffers(ctx.device, *ai, *cb);
    if result != .SUCCESS {
        log_error("vkAllocateCommandBuffers failed: %", result);
        return null;
    }
    bi: VkCommandBufferBeginInfo;
    bi.flags = .ONE_TIME_SUBMIT_BIT;
    vkBeginCommandBuffer(cb, *bi);
    return cb;
}

2. Recording: your calls become the hardware's packets, now

Every vkCmd* call appends the driver's own representation of that command to the buffer, at the moment you call it. That is the generic statement, and on RADV it is literal: radv_CmdDraw ends in radv_cs_emit_draw_packet, which writes a PM4 packet, PKT3_DRAW_INDEX_AUTO (opcode 0x2D) followed by the vertex count, into the indirect buffer. These are the same bytes the command processor will read; no other form of them exists. This is where the "bytecode" of the opening model lives, and who writes it: not the GPU, not the kernel, but the ICD on your CPU, inside your process, in memory you cannot see through the API. The draw list in record_scene becomes one such packet per entry, in the order of the list.

vkCmdBeginRendering(cb, *ri);

vkCmdBindPipeline(cb, .GRAPHICS, p.handle);
viewport := VkViewport.{0, 0, xx extent.width, xx extent.height, 0, 1};
vkCmdSetViewport(cb, 0, 1, *viewport);
scissor := VkRect2D.{.{0, 0}, extent};
vkCmdSetScissor(cb, 0, 1, *scissor);
for draws  vkCmdDraw(cb, 3, 1, xx (3 * it), 0);   // triangle `it` of the table

3. vkEndCommandBuffer: the stream is complete

End moves the buffer to the executable state. For the validation layer this is where recorded state is checked as a whole; for the driver it is where the stream is finalized: RADV flushes what it was holding, pads the indirect buffer to the alignment the hardware wants with no-op packets, and remembers its final size. After this call the buffer is a finished list of packets with a start address and a length, which is exactly what the next step hands to the kernel.

vkCmdEndRendering(cb);
vkEndCommandBuffer(cb);

4. Submit: an ioctl, not a translation

The correction that matters. vkQueueSubmit2 does not convert, copy or compile your command buffers. The driver builds a submission: on RADV, radv_amdgpu_winsys_cs_submit_internal gathers the addresses and sizes of the indirect buffers, the list of every buffer object they reference, the context from lesson 1, the engine and ring to use, and the sync objects to wait on and signal, and issues the DRM_AMDGPU_CS ioctl. In the kernel amdgpu_cs_ioctl parses those chunks, makes a job of them, and pushes it onto the context's scheduler entity; the DRM scheduler, when the entity's turn comes, writes a few packets into the hardware ring, among them an INDIRECT_BUFFER packet that points at your command buffer. The command processor reads the ring, follows that pointer, executes your packets from your buffer, and returns to the ring. Nothing was translated at any point after you recorded. The fence is the kernel's signal back: the job's completion fence, which vkWaitForFences waits on through the same context.

submit_ordered :: (ctx: *Gfx_Context, cbs: [] VkCommandBuffer) {
    infos := NewArray(cbs.count, VkCommandBufferSubmitInfo,, temp);
    for cbs  infos[it_index].commandBuffer = it;
    si: VkSubmitInfo2;
    si.commandBufferInfoCount = xx cbs.count;
    si.pCommandBufferInfos    = infos.data;

    fci: VkFenceCreateInfo;
    fence: VkFence;
    vkCreateFence(ctx.device, *fci, null, *fence);
    result := vkQueueSubmit2(ctx.queue, 1, *si, fence);
    if result != .SUCCESS  log_error("vkQueueSubmit2 failed: %", result);
    else                   vkWaitForFences(ctx.device, 1, *fence, VK_TRUE, 0xffff_ffff_ffff_ffff);
    vkDestroyFence(ctx.device, fence, null);
    vkFreeCommandBuffers(ctx.device, ctx.command_pool, xx cbs.count, cbs.data);
}

5. Order: within a buffer, across buffers, across submits

The specification calls the one ordering it defines submission order: the order of the submit calls on one queue, then of the submit infos within a call, then of the command buffers within an info, then of the commands as recorded. Within a render instance, rasterization order adds that for one sample, fragment operations and color writes happen in primitive order. Together they give the exercise its answer: in one buffer, later draws cover earlier ones; across two buffers in one submit, the second buffer's draws cover the first's; and across two submits, the second submit's do. Recording order never enters into it, which is what submission_order_not_recording_order shows by recording the loading buffer first and submitting it second.

What submission order does not give is memory visibility. Two render instances on one image, one per buffer, still need the barrier given.jai supplies as attachment_barrier, so that the first instance's color writes are finished and visible before the second loads them. Synchronization validation, which would catch its absence, stays off until lesson 5, which is where barriers get their own lesson.

second_buffer_draws_over_the_first :: (ctx: *Gfx_Context) -> bool {
    s := scene_begin(ctx);
    defer scene_end(ctx, *s);
    if !s.ok  return false;
    a, aok := clearing(ctx, *s, .[0, 1]);
    if !aok  return false;
    b, bok := loading(ctx, *s, .[2]);
    if !bok  return false;
    submit_ordered(ctx, .[a, b]);
    p := readback(ctx, *s.t, .COLOR_ATTACHMENT_OPTIMAL);
    return at(p, 64, 64, BLUE) && at(p, 64, 12, RED) && at(p, 115, 64, GREEN);
}

Elsewhere

Endnotes

Secondary command buffers

A common alternative to re-recording everything is a SECONDARY command buffer run from a primary with vkCmdExecuteCommands, which enables recording on several threads and reusing a recorded piece; useful for static scenery; the cost is the SECONDARY level, inheritance info that names the rendering it will run inside, and one more level of buffers to manage.

vkResetCommandPool with a pool per frame

A common alternative to freeing buffers one by one is a pool per frame in flight reset with vkResetCommandPool, which enables recycling every buffer of a frame at once; useful once there are many buffers per frame; the cost is one pool per frame in flight and the discipline of never resetting a pool whose frame the GPU is still on.

SIMULTANEOUS_USE_BIT

A common alternative to one-time buffers is VK_COMMAND_BUFFER_USAGE_SIMULTANEOUS_USE_BIT, which enables submitting one buffer again while it is still pending; useful for a buffer re-submitted every frame unchanged; the cost is that the driver may copy or patch it, and the fences of lesson 5 still decide when it may be reset.
