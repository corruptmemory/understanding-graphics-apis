Lesson 0 placed the loader, the layers and the ICD in the driver lane. This lesson follows the three objects every Vulkan program creates before it can do anything: the instance, which belongs to the loader; the device, which is the ICD's and, underneath it, the kernel's; and the queues, which are the channels work travels down. The harness's device.jai and exercise 1's solution are the code.

After this you can:

  • trace one vkCreateDevice call from your code through the loader's trampoline, the validation layer and into the ICD;
  • say what a queue family is, what a queue is in the ICD, and what it is in the kernel;
  • choose families for graphics and transfer on a device you have never seen, and defend the choice.

1. The instance is the loader's object

The harness asks for one layer and three extensions, and that is what shapes the chain the loader builds. Every function you call on a VkInstance, or on any handle that descends from it, enters a trampoline in libvulkan.so.1; the trampoline reads the dispatch table the handle points at and jumps to the first entry, the validation layer's version of the function; the layer checks its arguments and calls the next entry; the last entry is the loader's terminator, which calls the ICD. The rule that makes this work is that a dispatchable handle (VkInstance, VkPhysicalDevice, VkDevice, VkQueue, VkCommandBuffer) is a pointer whose first word is a pointer to that dispatch table; the loader writes it when the object is created, and every layer agrees to keep it. A VkBuffer or VkImage is not dispatchable: calls on those go through the device they belong to.

ici: VkInstanceCreateInfo;
ici.pNext                   = ifx options.sync_validation then cast(*void) *validation_features else cast(*void) *dbg;
ici.pApplicationInfo        = *app;
ici.enabledLayerCount       = layers.count;
ici.ppEnabledLayerNames     = layers.data;
ici.enabledExtensionCount   = exts.count;
ici.ppEnabledExtensionNames = exts.data;

result := vkCreateInstance(*ici, null, *ctx.instance);

2. Choosing a physical device

A physical device is a GPU as one ICD describes it. The terminator asks every ICD the loader found for its list and concatenates them: on this desktop that is one ICD and one device; on the hybrid laptop the Intel and NVIDIA ICDs each contribute one, and the order is whatever the loader's manifest scan produced. The harness turns each into a Device_Candidate and picks with a rule it can test without a GPU: the first discrete device that reports Vulkan 1.3 or newer, else the first device that does. The lowest index wins ties, so the choice is stable from run to run.

choose_physical_device :: (candidates: [] Device_Candidate) -> int {
    first_capable := -1;
    for candidates {
        if !supports_1_3(it.api_version)  continue;
        if it.device_type == .DISCRETE_GPU  return it.index;
        if first_capable == -1  first_capable = it.index;
    }
    return first_capable;
}

3. Queue families: what the hardware exposes

A queue family is a set of queues with the same capabilities, and underneath it is one kind of hardware engine. The ICD reports one family per engine kind it chooses to expose, with the flags that engine can honor and how many queues it offers. The specification adds a rule worth knowing before you write a chooser: a family with GRAPHICS_BIT or COMPUTE_BIT can always transfer, so reporting TRANSFER_BIT on it is optional. A transfer-only family, when there is one, is a DMA engine: cheaper to run alongside graphics and the right place for uploads once lesson 6 needs them.

RADV on this desktop reports five families: graphics with compute, transfer and sparse binding (one queue); compute with transfer and sparse binding (four queues, one per hardware compute pipe); video decode; video encode; and sparse binding alone. None is transfer-only: the compute family has COMPUTE_BIT, and the sparse family lacks TRANSFER_BIT, so it cannot copy at all. The chooser below therefore lands on 0 / 0 here, while on an NVIDIA or Intel discrete part it finds the DMA family the exercise's table cases describe.

choose_queue_families :: (families: [] VkQueueFamilyProperties) -> (choice: Queue_Choice, ok: bool) {
    graphics := -1;
    transfer := -1;
    for families {
        if graphics < 0 && (it.queueFlags & .GRAPHICS_BIT)  graphics = it_index;
        if transfer < 0 && (it.queueFlags & .TRANSFER_BIT) && !(it.queueFlags & (.GRAPHICS_BIT | .COMPUTE_BIT))  transfer = it_index;
    }
    if graphics < 0  return .{}, false;
    if transfer < 0  transfer = graphics;
    return .{xx graphics, xx transfer}, true;
}

4. vkCreateDevice: the ICD opens a kernel context

A logical device is the ICD's object for one physical device, and underneath it a kernel context: the kernel's record of one process using one GPU, with per-queue scheduling state hung off it. The create info names which families to open queues on, how many, and which features to turn on; here the 1.3 features the lessons rely on are chained through VkPhysicalDeviceFeatures2 in pNext, which is how everything after Vulkan 1.0 is asked for. Generically, the ICD validates the request against what it reported, allocates its device state, and asks the kernel driver for a context. On RADV that last step is radv_amdgpu_ctx_create issuing the DRM_AMDGPU_CTX ioctl to amdgpu, which answers with a context handle every later submission carries.

features13: VkPhysicalDeviceVulkan13Features;
features13.dynamicRendering = VK_TRUE;
features13.synchronization2 = VK_TRUE;
features2: VkPhysicalDeviceFeatures2;
features2.pNext = *features13;

dci: VkDeviceCreateInfo;
dci.pNext                = *features2;
dci.queueCreateInfoCount = family_count;
dci.pQueueCreateInfos    = qcis.data;

device: VkDevice;
result := vkCreateDevice(physical, *dci, null, *device);

5. A queue underneath: a scheduled channel to a ring

vkGetDeviceQueue allocates nothing: the queues were made with the device, and the call hands back a dispatchable handle to one of them. In the ICD a queue is a small object that remembers its family and so which engine kind its submissions target. In the kernel the picture is the one that explains ordering. amdgpu keeps, inside the context, one scheduler entity per engine and ring the process submits to; the DRM GPU scheduler pushes each entity's jobs, in the order they were pushed, onto the hardware run queue for that engine, and the hardware ring is where the command processor reads them. Two queues on one family are two entities feeding one kind of engine; the order between them is decided by the scheduler and by the sync objects you attach, never by the order of your calls. Lesson 4 is where a submission travels this path.

graphics, transfer: VkQueue;
vkGetDeviceQueue(device, choice.graphics_family, 0, *graphics);
vkGetDeviceQueue(device, choice.transfer_family, 0, *transfer);

Endnotes

MESA_VK_DEVICE_SELECT

A common alternative to choosing in code is MESA_VK_DEVICE_SELECT, which Mesa's device-select layer reads to reorder the physical device list; useful on the hybrid laptop when the integrated GPU comes first and you want the discrete one without touching the program; the cost is an environment variable and an implicit layer sitting in every instance's chain.

A second queue from a compute-only family

A common alternative is a second queue created from a compute-only family, which enables compute work that overlaps the graphics queue; useful for async compute once there is compute work; the cost is semaphores between the two queues and queue-family ownership transfers for every resource both touch.

queueCount greater than one

A common alternative is asking one family for several queues, which enables submitting from several threads without a lock around one queue; useful once recording is parallel; the cost is that the family must report that many, and ordering between the queues is by sync objects only.
