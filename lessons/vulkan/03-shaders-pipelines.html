Lesson 0 said that SPIR-V is compiled, not interpreted, and that the compiler is the driver. This lesson shows exactly when: a shader goes from GLSL on your disk, to SPIR-V words in your binary, to a module the driver merely keeps, to native instructions the driver produces when you create a pipeline. The pipeline is the other half of the story: everything you name in its create info is baked, and the few things you do not, the viewport and scissor here, are set per command buffer instead.

After this you can:

  • say what glslc produces, what vkCreateShaderModule does with it (a copy), and when the driver compiles it to GPU instructions;
  • list what a graphics pipeline bakes, why changing any of it means another pipeline, and which pieces dynamic state leaves out;
  • get a triangle's winding right in Vulkan's y-down clip space with back-face culling on.

1. GLSL to SPIR-V on your machine, before the program runs

The shader starts as text, and the first translation happens at build time, in your own process tree: first.jai runs glslc on every file under the target's shaders/ directory with --target-env=vulkan1.3, and what comes out is SPIR-V, a stream of 32-bit words that begins with the magic number 0x07230203. There is no GPU anywhere in that stream. It is a portable intermediate language: typed, structured, with the entry point and the interface named, and the same words work on every Vulkan driver. load_spirv then reads the file at compile time, so the words live in the Jai binary and the program never opens a shader file while it runs.

#version 450

// Three corners in clip space. Vulkan's y points down in framebuffer coordinates, and the
// specification's signed area a = -1/2 * sum(x_i * y_{i+1} - x_{i+1} * y_i) is positive for this
// order, so the triangle is front-facing under VK_FRONT_FACE_COUNTER_CLOCKWISE.
const vec2 corners[3] = vec2[3](
    vec2(-0.8,  0.8),   // bottom left
    vec2( 0.8,  0.8),   // bottom right
    vec2( 0.0, -0.8)    // top
);

void main() {
    gl_Position = vec4(corners[gl_VertexIndex], 0.0, 1.0);
}
for file_list(shaders_dir) {
    if !(ends_with(it, ".vert") || ends_with(it, ".frag") || ends_with(it, ".comp"))  continue;

    out := tprint("%1/%2.spv", out_dir, path_filename(it));
    result, output, error := run_command("glslc", "--target-env=vulkan1.3", "-o", out, it, capture_and_return_output = true);
load_spirv :: (path: string) -> [] u32 {
    data, ok := read_entire_file(path);
    assert(ok, "load_spirv: could not read '%' (run `first.jai - shaders <target>` first)", path);
    assert(data.count % 4 == 0, "load_spirv: '%' is % bytes, not a multiple of 4", path, data.count);
    words: [] u32;
    words.data  = cast(*u32) data.data;
    words.count = data.count / 4;
    assert(words.count > 0 && words[0] == 0x07230203, "load_spirv: '%' does not start with the SPIR-V magic number", path);
    return words;
}

2. vkCreateShaderModule copies words

A shader module, in the specification's words, "contains shader code and one or more entry points". That is all it is. On RADV the call copies the SPIR-V into driver memory, hashes it, and returns a handle; nothing is parsed into a GPU form, which is why the call is cheap and why you can destroy the module as soon as the pipeline that used it exists. The module is the driver's copy of your words, and the pipeline, not the module, is where the compiled code lives.

shader_module :: (ctx: *Gfx_Context, words: [] u32) -> VkShaderModule {
    ci: VkShaderModuleCreateInfo;
    ci.codeSize = xx (words.count * 4);
    ci.pCode    = words.data;
    m: VkShaderModule;
    result := vkCreateShaderModule(ctx.device, *ci, null, *m);
    if result != .SUCCESS  log_error("vkCreateShaderModule failed: %", result);
    return m;
}

3. vkCreateGraphicsPipelines: the driver compiles

The generic statement first: the driver compiles your shaders when you create the pipeline, so the pipeline object holds machine code for every stage plus the register values for every fixed-function stage you named: the primitive topology, the rasterizer's cull mode and front face, the sample count, the blend state, the attachment formats. Changing any of them means another pipeline, which is why programs create many and cache them. The compile is why the call is slow and why a loading screen hides it.

On RADV the chain is SPIR-V to NIR, Mesa's intermediate representation, then ACO, the AMD backend, which emits the instruction set of the chip in front of it. The dump below is the real vertex shader from the exercise, printed by the driver with RADV_DEBUG=shaders set in the environment when the test binary ran. Read the bottom up: s_endpgm ends the program; exp pos0 exports the clip position; buffer_load_b64 fetches one corner from the constant data, whose six words at the end are the three corners (0xbf4ccccd is -0.8, 0x3f4ccccd is 0.8); and RADV has turned the vertex shader into a primitive shader ("as ESGS", the RDNA next-generation geometry path), which is why it also exports the primitive. This is what "native" means: the shader cores run these words, not the SPIR-V.

gpci: VkGraphicsPipelineCreateInfo;
gpci.pNext               = *rendering;
gpci.stageCount          = stages.count;
gpci.pStages             = stages.data;
gpci.pVertexInputState   = *vertex_input;
gpci.pInputAssemblyState = *input_assembly;
gpci.pViewportState      = *viewport_state;
gpci.pRasterizationState = *raster;
gpci.pMultisampleState   = *multisample;
gpci.pColorBlendState    = *blend;
gpci.pDynamicState       = *dynamic;
gpci.layout              = p.layout;
gpci.renderPass          = null;
result = vkCreateGraphicsPipelines(ctx.device, null, 1, *gpci, null, *p.handle);

Metal

4. Dynamic state: set per command buffer, not baked

The pipeline asked for one viewport and one scissor but gave their values as dynamic. The specification's rule is that binding a pipeline applies every piece of its state that is not dynamic to the command buffer, and the dynamic pieces are set by their own commands, persisting for the lifetime of the command buffer or until set again. So record_triangle binds the pipeline, then sets the viewport it was given and a scissor over the whole extent, and the same pipeline serves the 128 by 128 test target, the half-width viewport of the fourth test, and the 640 by 480 window. In the driver these are register values written into the command stream at draw time rather than baked into the pipeline's state words.

vkCmdBindPipeline(cb, .GRAPHICS, p.handle);
vp := viewport;
vkCmdSetViewport(cb, 0, 1, *vp);
scissor := VkRect2D.{.{0, 0}, extent};
vkCmdSetScissor(cb, 0, 1, *scissor);

Elsewhere

D3D12
RSSetViewports and RSSetScissorRects on the command list; viewports and scissors are always dynamic, never part of the pipeline state object
Metal
setViewport and setScissorRect on the render command encoder, likewise never baked

5. The draw and the winding

vkCmdDraw(cb, 3, 1, 0, 0) asks for three vertices and one instance; with no vertex buffers bound, the only thing the vertex shader receives is gl_VertexIndex, 0 then 1 then 2, which is what indexes the constant array. In the driver the call appends a draw packet to the command stream (lesson 4), and on the GPU the command processor reads it, the shader cores run the ISA above once per vertex, and the rasterizer decides which pixels the triangle covers, after it has decided whether to keep the triangle at all.

That decision is the one most people get wrong when they arrive from OpenGL. The specification computes a signed area in framebuffer coordinates, where y points down: a = −½ Σ (xi yi⊕1 − xi⊕1 yi), and "VK_FRONT_FACE_COUNTER_CLOCKWISE specifies that a triangle with positive area is considered front-facing". For the corners in the order bottom left, bottom right, top the sum is −2.56, so a is +1.28 and the triangle is front-facing; with back-face culling on it shows. The same three corners with CLOCKWISE leave the target black, which is the second test, and with NONE the winding stops mattering, which is the third.

vkCmdDraw(cb, 3, 1, 0, 0);
triangle_culled_when_front_face_is_clockwise :: (ctx: *Gfx_Context) -> bool {
    p, ok := draw_once(ctx, .CLOCKWISE, .BACK_BIT, FULL);
    if !ok  return false;
    return expect_region_solid(p, 0, 0, 128, 128, 0, 0, 0, 255);
}

Endnotes

VkPipelineCache saved to a file

A common alternative to compiling at every start is a VkPipelineCache whose blob is saved to disk and loaded next time, which enables the driver to skip the compile for pipelines it has seen; useful once there are dozens of pipelines; the cost is saving and loading the blob and checking its header against the driver and device before trusting it.

Vulkan 1.3 dynamic state for cull mode, front face and topology

A common alternative to one pipeline per winding is the Vulkan 1.3 dynamic states (from VK_EXT_extended_dynamic_state), which enable vkCmdSetCullMode, vkCmdSetFrontFace and vkCmdSetPrimitiveTopology per draw; useful when one pipeline must serve both windings; the cost is more vkCmdSet* calls before every draw, and state that is no longer visible in the pipeline.

VK_KHR_pipeline_executable_properties

A common alternative to RADV_DEBUG=shaders is VK_KHR_pipeline_executable_properties, which enables reading the compiled code and its statistics back through the API; useful for seeing what any driver made without an environment variable; the cost is enabling the feature and setting VK_PIPELINE_CREATE_CAPTURE_INTERNAL_REPRESENTATIONS_BIT_KHR on the pipeline.
