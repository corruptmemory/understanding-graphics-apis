This page is the template every lesson is copied from, and its content is real: the five steps below walk the harness's own self-check, clear_color_reads_back, which clears a 64 by 64 image to one color on the GPU and reads the pixels back to the CPU. Every snippet is lifted from code in this repository that compiles and runs.

After this you can:

  • say which of the five steps touches the GPU, and which only touch memory the driver owns;
  • explain in one sentence why the clear and the readback need a barrier between them;
  • point at the line where the CPU last has control before the kernel takes the work.

1. Create an offscreen color target the GPU can render into and the CPU can read back

create_target makes a VkImage with its memory and a view, plus a host-visible buffer for the readback. All of it is CPU-side bookkeeping: the driver allocates GPU memory and records the handles, but no GPU work is queued yet. begin_commands hands back a command buffer in the recording state, which is also just memory the driver owns.

t := create_target(ctx, 64, 64);
defer destroy_target(ctx, *t);
cb := begin_commands(ctx);

2. Move the image into the layout the color-attachment path wants

The image starts UNDEFINED. transition_image records a barrier that puts it into COLOR_ATTACHMENT_OPTIMAL before anything writes to it. Recording the barrier appends to the command buffer; the layout change itself happens on the GPU when the buffer runs. This is a barrier, and lesson 5 opens barriers up; here it is one call.

transition_image(cb, t.image, .UNDEFINED, .COLOR_ATTACHMENT_OPTIMAL,
                 VK_PIPELINE_STAGE_2_NONE, VK_ACCESS_2_NONE,
                 VK_PIPELINE_STAGE_2_COLOR_ATTACHMENT_OUTPUT_BIT, VK_ACCESS_2_COLOR_ATTACHMENT_WRITE_BIT);

3. Record a clear with dynamic rendering: no render-pass object, just an attachment and a color

A VkRenderingAttachmentInfo names the view and asks for a CLEAR load with the color 0.25, 0.5, 0.75. vkCmdBeginRendering and vkCmdEndRendering bracket an empty pass, which is enough to make the clear happen. Still CPU memory: the driver is appending its own representation of these commands to the buffer.

att: VkRenderingAttachmentInfo;
att.imageView = t.view; att.imageLayout = .COLOR_ATTACHMENT_OPTIMAL;
att.loadOp = .CLEAR; att.storeOp = .STORE;
att.clearValue.color._float32 = .[0.25, 0.5, 0.75, 1.0];
ri: VkRenderingInfo;
ri.renderArea = .{.{0, 0}, .{64, 64}}; ri.layerCount = 1;
ri.colorAttachmentCount = 1; ri.pColorAttachments = *att;
vkCmdBeginRendering(cb, *ri);
vkCmdEndRendering(cb);

4. Submit the command buffer and wait for the fence: this is where the work leaves the CPU

submit_and_wait wraps vkQueueSubmit2 and a fence. Submit is where the driver translates the recorded commands into its own command stream and hands them to the kernel driver, which schedules them on the GPU's queue. The fence wait then blocks the CPU until the GPU signals that the clear is done. Everything the three lanes show lit for this step happens inside that one call.

submit_and_wait(ctx, cb);

5. Read the pixels back and check them against what the clear asked for

readback records a copy from the image into the host-visible buffer, submits it, waits, and maps the buffer. The copy runs on the GPU; the map and the byte-for-byte comparison run on the CPU. The expected values are the clear color scaled to bytes: 64, 128, 191, 255.

p := readback(ctx, *t, .COLOR_ATTACHMENT_OPTIMAL);
return expect_pixel(p, 32, 32, 64, 128, 191, 255) && expect_region_solid(p, 0, 0, 64, 64, 64, 128, 191, 255);

Endnotes

Loading instead of clearing

A common alternative is VK_ATTACHMENT_LOAD_OP_LOAD, which keeps whatever is in the image; useful for drawing over a previous frame or updating part of it; the cost is that the image must already be in a defined layout with valid contents, so you own one more transition at initialization.

A transfer queue for the copy

A common alternative is a dedicated transfer queue for the readback copy, which keeps copies off the graphics queue; useful when uploads and readbacks are frequent; the cost is a queue-family ownership transfer for the image and a second queue plus semaphore at setup.
